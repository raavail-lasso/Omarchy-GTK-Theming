GTK 4 apps that follow the theme

How the gtk4-live-css project makes open GTK 4 apps repaint when the theme changes, why we aren't installing it, and our own plan to get the same result on Omarchy without replacing a system package.

01 · GOALThe goal

When you switch Omarchy themes, the bar, terminals and Hyprland borders change straight away. GTK 4 apps like Nautilus don't. They keep stock Adwaita colours, and even with a custom stylesheet they only pick it up the next time they start. We want:

  1. GTK 4 apps that use the current Omarchy theme's colours.
  2. Windows that are already open to repaint when the theme changes, without restarting.
  3. No replacing Arch's gtk4 package.

02 · THE PROBLEMWhy GTK 4 apps don't follow themes

  • Theme switching doesn't work for libadwaita apps. Most GTK 4 apps (Nautilus included) are built on libadwaita, and libadwaita sets GTK's theme name to Adwaita-empty. That means "install a GTK theme and switch to it" does nothing. We confirmed this string is in /usr/lib/libadwaita-1.so.0 on this machine.
  • The one file they do honour is read once. GTK 4 loads ~/.config/gtk-4.0/gtk.css at the highest priority, above libadwaita's own styles, so it can recolour everything. But it reads the file only once, when the app starts, and never checks it again.
  • Colour mode alone is too coarse. Omarchy already switches light/dark (omarchy-theme-set-gnome), and libadwaita does follow that live. But that only picks Adwaita light or dark, not the theme's actual colours.

03 · RESEARCHHow gtk4-live-css does it

saneaspect/gtk4-live-css is Arch's normal gtk4 package rebuilt with one patch (about 120 lines) to gtk/gtksettings.c. It doesn't use a theme or a config trick. It changes GTK itself.

  1. When GTK loads the user's gtk.css into its style provider, the patch keeps a pointer to that provider.
  2. It starts a file watcher (GFileMonitor, which uses inotify) on the file. If the file is a symlink, it also watches whatever the link points at, so it catches both a swapped link and a rewritten file.
  3. When the file changes, it waits 150 ms (theme switchers write several files in a row), then reloads the same provider with gtk_css_provider_load_from_path().
  4. GTK sees the provider changed and restyles every open window, the same as if the app had just started.

The rest of the repo is packaging. A daily GitHub Action takes Arch's latest gtk4 recipe, adds the patch, builds it, and publishes it as a pacman repo. The package replaces gtk4.

Why we're not installing it: it swaps out a core system library for an unsigned, single-maintainer build. When the GTK developers change the code the patch touches, the daily build stops and you also stop getting GTK updates until the patch is fixed.

04 · DONEPart 1: gtk.css from the Omarchy theme

Omarchy already has a template system. omarchy-theme-set-templates renders every ~/.config/omarchy/themed/*.tpl into the current theme folder, replacing placeholders like {{ background }} with values from the theme's colors.toml. So this part needed no code:

  • A template at ~/.config/omarchy/themed/gtk.css.tpl that overrides libadwaita's named colours (@define-color window_bg_color, accent_bg_color, sidebar, cards, popovers, dialogs, and the status colours). libadwaita 1.10 still builds its colours from these names, so overriding them recolours the apps.
  • A symlink from ~/.config/gtk-4.0/gtk.css to ~/.local/state/omarchy/current/theme/gtk.css. Omarchy swaps the whole theme folder on each switch but keeps the same path, so the link always points at the current theme.

Result: every GTK 4 app you start uses the theme's colours. We checked that the generated file has every placeholder filled in and the colours match colors.toml. Not done yet: looking at a GTK 4 app on screen, so some colour choices may need a tweak.

06 · TRADE-OFFSOption 2 downsides, in plain words

LD_PRELOAD is a Linux feature that says "load this extra library into a program before it starts". Our library checks whether the program is a GTK 4 app. If it is, it watches gtk.css and repaints the app's windows when the file changes. If it isn't, it does nothing.

If we load it into every program (the simple version), the downsides are:

  1. It sits in every program. Your terminal, browser and everything else carry it, doing nothing. It costs a few KB per program.
  2. A bug could crash apps. Because it runs inside other programs, a mistake in our code could take down whatever it's loaded into. This is the real risk.
  3. Flatpak apps don't get it. They run in a sandbox that doesn't see the library.
  4. Warning noise. 32-bit programs (Steam, Wine) may print a harmless "wrong ELF class" warning.
  5. It's a hidden piece. Months later you might forget it's loaded when an app acts oddly.
  6. You need to log out and back in once for it to take effect.

07 · TRADE-OFFSOption 1 downsides, in plain words

  1. You lose what's open: windows, tabs, the folders you were in, a half-done file copy, unsaved text.
  2. It doesn't always reopen cleanly. Windows can come back in the wrong place, or not at all.
  3. You have to list the apps. New GTK apps stay in old colours until you add them.
  4. The switch looks jumpy. GTK windows vanish and pop back up.
  5. Some apps shouldn't be restarted, like an installer halfway through, so they'd have to stay in old colours.

Its upside is that nothing runs inside other programs, so it can't cause mystery crashes.

09 · PLANSteps

  1. done Generate gtk.css from each Omarchy theme and link it into ~/.config/gtk-4.0/ (section 04).
  2. done Write the library (gtk-live-css.c, about 60 lines of C) with all the safety measures above. When it's loaded into a GTK 4 app, it:
    • waits until GTK has opened its display;
    • adds its own CSS provider, loading ~/.config/gtk-4.0/gtk.css at a priority just above GTK's own copy, so our fresh copy beats GTK's stale one;
    • watches the file (and the symlink's target), waits 150 ms after a change, then reloads, the same as the patch.
  3. done Build it to ~/.local/lib/gtk-live-css.so with the system gcc.
  4. done Enable it for Nautilus only. Nautilus is usually started over D-Bus (DBusActivatable=true), so we override its D-Bus service file. We also override its launcher (.desktop) file for launchers that run the command directly. Both just add env LD_PRELOAD=~/.local/lib/gtk-live-css.so in front of the normal command.
  5. done Quit Nautilus once (nautilus -q), reopen it, switch themes and watch it repaint. Confirmed working on 2026-10-22: library loaded, both folders watched, colours look right. Now: use it for a few days.
  6. done Added the other GTK 4 apps on this machine (Papers, Transmission, Tensaku) through an APPS list in install. Papers was checked: started from its launcher file, it loaded the library and watched gtk.css. To add more, see the README.
  7. done Covered GTK 3 apps and GTK 4 apps that don't use libadwaita's styles, with adw-gtk3 and our own Adwaita / Adwaita-dark themes (section 10). Checked with screenshots of Transmission, Tensaku, Evince and Papers.

Lesson from testing

The first test failed because LD_PRELOAD applies to every program in a chain, including wrappers like timeout or env. The library removed LD_PRELOAD inside the wrapper, so the real app never got it. Fix: it now leaves the environment untouched unless it's actually inside a GTK 4 app.

Lesson from the first real launch

After the overrides were in place, Nautilus still started without the library. Omarchy's Super+Shift+F runs omarchy-launch-nautilus, which starts nautilus by name through uwsm-app. That skips both the .desktop file and D-Bus. A ~/.local/bin/nautilus wrapper wouldn't help either, because ~/.local/bin comes after /usr/bin in Hyprland's PATH. Fix: the two keybindings now run Omarchy's launch scripts with env LD_PRELOAD=... in front. The variable passes through bash, setsid and uwsm-app untouched (none of them are GTK) and reaches Nautilus.

10 · COVERAGEGTK 3 apps and GTK 4 apps without libadwaita

After adding Papers, Transmission and Tensaku, only Papers picked up the colours. Screenshots showed Transmission and Tensaku in GTK's built-in grey-and-blue look, even though the library had loaded in both.

Why

Our gtk.css changes colours by name (for example "window background = #0A0E11"). That only works when the app's stylesheet looks colours up by name:

  • libadwaita apps (Nautilus, Papers) do, so they work.
  • Transmission doesn't use libadwaita, and Tensaku links it but doesn't use its styles. Both fall back to GTK's built-in theme, which has its colours hard-coded into every rule, so there are no names to change.
  • GTK 3 apps (Evince, Disks) have the same problem with GTK 3's built-in Adwaita.

Fix: adw-gtk3 plus a small custom theme

adw-gtk3 (Arch package adw-gtk-theme) is a GTK 3 and GTK 4 theme that makes non-libadwaita apps look like libadwaita apps. We checked inside the package that it looks colours up by the same names (--window-bg-color: @window_bg_color), so it can follow our colours. libadwaita apps ignore GTK themes, so it can't affect Nautilus or Papers.

  • GTK 4: install creates two themes in ~/.local/share/themes/, named Adwaita (light) and Adwaita-dark. Each one imports adw-gtk3, then our generated gtk.css.
  • GTK 3: a second template, themed/gtk3.css.tpl, is rendered into the theme folder on every switch. It imports the light or dark adw-gtk3, chosen by the theme's {{ mode }}, then our colours. ~/.config/gtk-3.0/gtk.css links to it. GTK 3 loads that file above whatever theme is active, so the theme name doesn't matter (see the third trap below).
  • Omarchy's omarchy-theme-set-gnome sets the GTK theme to Adwaita or Adwaita-dark on every switch, depending on the theme's mode. GTK finds ours before its built-in copies, so Omarchy's own reset selects them. No hook is needed.
  • On a dark-to-dark switch the theme name doesn't change, so GTK doesn't reload the theme. The library reloads gtk.css above the theme, so apps in APPS repaint anyway. On a light/dark switch the name changes and GTK reloads the theme too.

Three traps we hit

  • The dark file. In dark mode GTK loads the theme's gtk-dark.css. If that file is missing, it silently falls back to its built-in theme, even though it reports the theme name you set. Our first themes only had gtk.css, so nothing changed. A small probe program showed the theme name was right but the colours were GTK's own. Both files are written now.
  • The accent colour. adw-gtk3's GTK 4 tweaks file pins the accent to blue (--accent-bg-color: var(--accent-blue)), so Tensaku's main button stayed blue. The GTK 4 theme files add :root { --accent-bg-color: @accent_bg_color; } after the imports. GTK 3 doesn't support CSS variables and doesn't need this.
  • libhandy and GTK 3's built-in Adwaita. At first GTK 3 also used the Adwaita / Adwaita-dark theme trick. A GTK 3 probe program got our colours, but Evince and Disks stayed stock grey. Both use libhandy (the GTK 3 predecessor of libadwaita), which switches Adwaita-dark to Adwaita plus dark mode. Probes showed GTK 3 always loads its built-in Adwaita; only Adwaita-dark can be overridden from ~/.local/share/themes. That also meant light Omarchy themes would have broken every GTK 3 app. Fix: GTK 3 now uses ~/.config/gtk-3.0/gtk.css, which applies whatever the theme name is. Checked with screenshots of Evince, Disks and bssh, and a probe with the light name.

Why Transmission and Tensaku took about 8 seconds

The first version used Omarchy-GTK themes plus a theme-set hook. During a switch, Omarchy's omarchy-theme-set-gnome reset the theme to Adwaita-dark almost immediately, putting Transmission and Tensaku on GTK's built-in theme, where our colours can't apply. Our hook only switched it back at the very end, because Omarchy runs hooks after all its own theme commands, one after another in alphabetical order. folder-icons.sh (from Omarchy Folder Icons) ran first and takes about 7 seconds to re-render the icons. Nautilus wasn't affected because libadwaita ignores GTK themes.

Fix: name our themes Adwaita and Adwaita-dark. GTK looks in ~/.local/share/themes before its built-in copies (tested with GTK 3 and GTK 4 probe programs), so Omarchy's reset itself picks our adw-gtk3 themes. The theme never leaves adw-gtk3, the hook is gone, and the library repaints in about 150 ms. A timing test confirmed it: with Transmission and Tensaku open, a screenshot 0.5 seconds after the change showed the new colour, and 0.5 seconds after restoring showed the theme colour again.

How Aether updates so quickly

Aether (the Omarchy theming app) isn't themed through GTK at all. It's a Wails app: a Go program with a web interface (Svelte) inside a WebKitGTK view. GTK 3 only provides the window frame. internal/theme/watcher.go checks the timestamp of ~/.local/state/omarchy/current/theme/colors.toml every 2 seconds. When it changes, Aether reads the colours and sends them to the web page as a theme-colors-changed event, and the page updates its CSS variables. That file appears as soon as Omarchy swaps the theme folder in, early in a switch, so Aether updates within about 2 seconds. It doesn't wait for hooks, which is the same reason Nautilus is fast with our library.
